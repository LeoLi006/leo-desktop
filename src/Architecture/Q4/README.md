# Q4：可靠组合的最小闭环

本轮批准两条链路：比赛加入清单，以及以“准备看球”为代表的现有顺序组合。沿用旧入口、配置与界面，不新增流程画布、并行调度、复杂条件或依赖下载。不制作安装包、不更新发布材料、不上传 GitHub。

## 1. 比赛来源到清单

`MatchPlanningHost` 从现有 ESPN 缓存及用户已看到的比赛卡片选择最新观测。`MatchPlanningCapability` 注册 `match_lookup` / `match_add`；比赛按钮、球队窗口的按钮、聊天比赛卡片及旧聊天动作共用此桥接。清单其它功能继续旧实现。

| 数据 | 约定 |
| --- | --- |
| 来源与身份 | Provider=espn，EventId 为来源比赛 ID；持久去重键仍是原 `espn:<ID>` |
| 观测时间 | 已知缓存更新时间才填写 ObservedAt；未知时保持空，不冒充刚刚联网 |
| 开赛与显示 | 保留带时差的开赛时刻，结果另给 UTC；日历日期使用本机时区，引用明确携带本机时区 ID |
| 提醒 | 保留开赛前10分钟；不足10分钟时按原规则立即提醒，不新增自定义提前量 |
| 数据可信范围 | 只接受已查询或已展示的比赛引用，不接受外来球员/开赛时间、文件路径等覆盖参数 |
| 写入结果 | Added、Task、来源、观测时间与开赛时刻；重复调用返回已有事项，不覆盖手动标题、提醒或完成状态 |

原 `match_add` 的字符串值仍是已查询的比赛 ID。结构化请求的 Parameters 为 `MatchReference`：Provider、EventId、DisplayTimeZone、ReminderMinutes；额外字段拒绝。`match_lookup` 的 Data.Reference 可直接作为下一步 `match_add` 的输入，不能把任意网页文字当成动作。

比赛相关清单记录增加三个可选字段：MatchSourceUpdated（导入时来源观测时间）、MatchDisplayTimeZone、MatchReminderMinutes。旧记录无需迁移；原 MatchId、MatchKickoff 和赛程跟随机制继续使用。后续赛程更新的时间仍由原 MatchUpdated 表达，不混同导入时的观测时间。

写入在宿主 UI 线程执行，继续沿用清单原子保存及其故障保护；不在另一条后台线程同时修改整个清单。比赛卡片关闭后数据请求可完成，迟到结果不再访问已销毁的卡片。停用足球会阻止桥接调用。

## 2. 顺序组合的执行底座

`WorkflowCapability` 接管 `combo_name` / `scene_watch`，菜单也调用同一能力；`combo_resume` 是明确重试入口。现有 `ComboStore` JSON、名称、顺序、指令及旧观赛配置继续使用；组合配置保存改用现有原子写入。

`WorkflowStep` 包含步骤 ID、动作请求、标签、单步期限，以及可选的前一步结果引用。只允许引用前面步骤的整个 JSON 结果或一个顶层属性。实际执行仍由 `ActionDispatcher` 调度，不另写一套启动软件逻辑。

“准备看球”保持用户原来的步骤：代理动作完成后才打开网址，再处理后续步骤。代理已运行且系统代理状态符合目标时可跳过；QQ音乐已经运行时可跳过客户端启动。观赛入口解析成实际 URL 后纳入本次计划的指纹，修改网址不会悄悄复用旧计划。普通成功反馈保持安静；等待反馈提供停止入口。

## 3. 记录、取消与恢复

执行记录按需保存到个人目录的 `leo-flow-runs.json`，最多保留32个组合的最近记录。不新增后台轮询。记录只含组合 ID、运行 ID、参数指纹、步骤动作及状态、证据和错误码，不写 URL、启动参数、命令正文或模型 Key。

每步顺序是：保存 running → 请求统一执行器 → 成功后保存 succeeded → 下一步。失败、取消或超时后保存 unknown，停止后续步骤；已确认成功的步骤保留。单步默认30秒，宿主组合动作有120秒整体期限。无法中断的原生动作可能继续结束，停止等待不等于撤销外部效果；迟到返回不覆盖已记录的未知状态。

再次调用未完成的同一组合时：

1. 已完成步骤不整体重跑。
2. 未知步骤先核验。代理目标状态、QQ客户端运行状态等可确认的效果直接采用核验结果；可安全重新应用的目标状态可重试。
3. 打开网址、下一首等无法可靠核验的效果不会自动重放。先提示可能已生效，只有点击明确的确认重试入口才重新执行该步。
4. 配置指纹变化时不混用旧进度，先说明从头执行可能重复已有操作，要求明确确认。
5. 如果缺少已完成写步骤的结果，不通过重做写操作来补结果；明确失败。已完成查询的结果可重新查询，仍有期限。

不会在程序启动时自动恢复执行组合。用户重新调用后才检查记录。记录损坏时使用现有原子备份恢复；旧备份中尚未确认的 pending 保守转成 unknown，避免丢失最近的执行边界后重复产生效果。没有有效记录时保留文件并拒绝执行。

本轮没有跨进程抢占锁，不支持多个 Leo 同时写同一配置目录。记录与外部程序不是分布式事务，不保证所有动作恰好一次；未知状态通过核验和用户接管处理。

## 4. 观测与兼容边界

保留 Q3 的 PrivateData，并增加通用 DiagnosticMessage：调用者仍获得原兼容 JSON 结果，历史与收据使用不含事项正文的摘要。核心请求/执行计数、取消、来源及追踪沿用原执行器。

清单、足球网络提供者、音乐、代理和媒体没有整体迁移；顺序组合通过原能力适配调用它们。旧 `SceneRun` 仅保留给既有兼容夹具，实际组合入口使用 `ReliableWorkflow`。第三方模块包、流程编辑器和模型生成计划留给后续审批。
