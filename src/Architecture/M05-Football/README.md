# M05 第四批：足球查询能力迁移

日期：2026-10-20。保留 ESPN 来源、关注目录、国家队赛事选择、页面和文件格式；本批不新增足球功能。

## 统一路径

`FootballCapability` 注册现有 `football_facts`、`football_open`，并提供宿主内部 `football_schedule`、`football_team`、`football_events` 查询。`FootballQueries` 负责缓存快照、刷新串行、配置代际、取消和保存；`FootballClient` 供现有界面使用。

| 入口 | 路径 |
| --- | --- |
| 足球主页、手动刷新 | 共享客户端 → 注册赛程查询 |
| 球队近期比赛、联赛/国家队积分榜 | 同一球队查询；按球队及赛事区分缓存 |
| 聊天本地查询及分析事实 | 旧 football_facts 适配 → 同一赛程/球队查询 |
| 模型工具 | 注册表发现公开事实查询，保留实际编号校验 |
| 比赛加入清单、比赛参数查询 | 从共享已查询快照解析；复用 Q4 来源校验及 M05 清单写入 |
| 已加入清单比赛的后台校时 | 内部比赛详情查询 → 原 ESPN summary 提供者 → 统一清单服务 |
| 悬停摘要 | 读取共享缓存快照，不新增联网轮询 |

独立预览/窗口也使用同一种能力实现；预览不联网、不保存缓存。正常宿主各窗口共享客户端，子页面关闭只取消自己的等待。宿主退出释放查询服务，模块停用取消请求并阻止旧结果发布。

底层 `FootballFeed.FetchAsync`、`TeamData.Fetch` 和 `MatchSyncService.FetchIds` 只提供数据，缓存写入集中到查询服务。已有手动联网诊断仍可直接检查底层解析/提供者，不构成正常界面的第二套业务入口；本批没有运行这些联网诊断。

## 缓存与失败

- 保留原赛程和球队 JSON；原子替换、有效前版恢复及损坏副本保留使用已有宿主存储。缓存不是个人任务数据库，不把损坏文件当作有效内容。
- 正常查询沿用10分钟缓存；显式刷新跳过新鲜缓存。更新关注后原赛程快照失效，不能把旧关注下的结果当作新结果。
- 相同在途请求经分发器合并。聊天旧查询适配到规范化内部请求，因此能与窗口共享同一次查询；不同文本表示的同一资源还有服务层串行及刷新修订检查。
- 查询结果为独立快照，窗口修改列表不能改变共享缓存。查询失败保留原内容及时间，返回 `Stale`/失败标记；没有缓存则返回空快照并明确过期/失败。
- 球队赛程和积分榜分别保留最后成功时间。某一部分失败时强制保留该部分旧内容，不能用失败响应中的空列表清掉已有数据。
- 取得新结果但缓存保存失败时，保留本次内存结果并返回 `CacheSaved=false`，界面提示未保存，不谎称已经落盘。
- 比赛详情查询只接受最多24个真实格式编号，使用有界短缓存；失败/缺失编号不会合成比赛或清空清单提醒。成功详情进入共享来源快照。

`football_facts` 保留原 view 及聊天 JSON 形状，增加明确过期/保存状态；数据仍带 ESPN 来源、更新时间和实际比赛编号。诊断结果省略查询正文，实际数据只在请求结果中提供。

## 取消与一致性

调用者可分别取消；只要还有订阅者，同一次查询继续执行。最后等待者取消、模块停用、宿主关闭时停止相关等待。提供者即便忽略取消，完成后也须通过取消令牌、关注配置及代际检查才能发布/保存，旧结果不能覆盖重新启用后的结果。

分发器新增显式 `IRestartableQueryModule` 选择性标记：只有声明为只读且支持代际丢弃的足球查询，才允许新请求替换已取消的执行槽；宿主服务仍按资源串行。本机程序启动等外部操作维持原占用保护，不因超时/取消而并行重启同一操作。

模型只发现公开查询与打开窗口；内部缓存、详情和强制刷新动作不作为模型工具提供。Q5 本轮实际比赛编号、多候选澄清、修改预览确认及 Q4 比赛来源校验继续有效。没有改变模型后端或调用收费 Key。
