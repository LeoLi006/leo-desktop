# Q1：稳定底座与模块化的准备工作

本批只做盘点、测量和接口草案，不迁移业务，不改变 Leo 的功能开关与使用方式。没有引入新依赖，没有制作安装包或 GitHub 发布材料。

## 阅读顺序

1. [现状、依赖与旁路](INVENTORY.md)：各功能由谁负责、从哪里调用、有哪些后台活动和数据、哪些路径仍未统一。
2. [63 个现有动作逐项清册](ACTIONS.md)：保留精确动作 ID、当前归属和源码引用，便于后续逐项迁移。
3. [契约草案](CONTRACT.md)与[四类样例](examples.json)：模块、动作、请求、结果、宿主服务和入口贡献的共同形状；不是已上线协议。
4. [测量方法](BASELINE.md)、[数值摘要](MEASURED.md)和[聚合数据](measurements.json)：同机重复样本与限制，不把预览或短时计数说成全天稳定性。
5. [兼容与迁移](MIGRATION.md)：旧动作、扩展、组合、配置和个人数据怎么保留，每批如何验收和回退。

## 本轮形成的决策

- 继续利用 ActionDispatcher 和已有业务服务，不新建平行执行体系。先用适配器将旧接口接入，再逐步迁移旁路。
- 第一个试点建议选“自定义本机应用启动”，而不是同时重构所有功能。它能验证注册、启停、入口和结果，又不必先处理复杂清单/比赛/播放逻辑。
- “大脑”未来只负责理解、选择能力和组合计划；能力目录、执行、取消及结果确认由公共底座负责。本地明确指令继续无需模型。
- 隐藏、停用、卸载和删除个人数据分开；关闭窗口也不等于停用共享能力。
- 证据、并发和副作用分开描述。发出播放请求不冒充已播放，取消不冒充撤销，重复点击不统一套用同一种合并方式。

## 验证工具

`q1_audit.py` 只读源码和人工样例，生成动作清册并验证草案的正例/反例。`Measure-Q1.ps1` 和 `BaselineProbe.cs` 只在显式调用时执行；`summarize.py` 从允许的数值计数生成摘要。原始输出在 `.build/q1`，不进入版本库。

当前运行时仍是旧协议。通过草案检查不代表运行时已经具备新契约中的所有能力；Q2 需另行审批与实现。
