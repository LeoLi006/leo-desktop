# 便签并发波动：证据与定点修复

日期：2026-10-21。只覆盖便签保存、原子替换与直接相关请求语义。未改超时、数量断言或存储格式。

## 观察到的失败

Q3原25请求夹具补充每个请求的序号、状态、错误码、耗时、异常类型及HResult低位错误号；批次记录请求数量、成功/失败/取消、内存和磁盘条数。只在隔离测试报告记录，不加入生产日志，不记录正文、完整参数、路径或请求业务标识。

修复前新专项第二轮25次写入中1次失败，约118ms返回storage_failed / IOException，原生码1175（本机Windows错误解释：无法删除要被替换的文件）。成功回执24，实际提交、内存及磁盘均24。三轮中其余两轮25次全部成功。

因此这次复现是原子文件替换返回错误，不是15秒请求超时，也没有证据表明回报成功后丢失数据。没有证据确定是哪个外部进程或文件系统因素导致1175，不指认杀毒、同步软件等原因。早期Q3只有数量断言失败，不能倒推它们全部是同一原因。

## 修复范围

NoteStore默认写入选用AtomicJson.WriteNotes；其他调用继续使用AtomicJson.Write。二者共用原子写入实现，只有便签路径启用以下策略：

1. 仅捕获原子File.Replace抛出的IOException且HResult精确为0x80070497（1175）。BeforeReplace钩子及其他阶段失败不重试。
2. 最多在首次失败后重试3次，等待20、40、60ms，总额外等待最多120ms，仍使用原临时文件，不重新执行便签事务或生成新事项。
3. 等待前后均确认目标文件文本仍等于替换前原文、临时文件文本仍等于待提交内容；读失败、缺失或变化立即停止。此检查不是对外部写者的跨进程锁，不扩展为并发编辑协议。
4. 只有最终替换成功才沿原路径发布内存快照和Changed；持续失败继续返回storage_failed，临时文件按原finally清理。备份、原格式、取消后可能已提交的说明及进程内有界重放不变。

重试仍在原原子保存锁内，罕见失败时可能使其他本地原子写入多等待上述时间，不延长动作期限。不对普通共享冲突32、权限问题、任意IOException或其他模块的写操作自动重试。

AtomicJson.ReplaceOverride仅是显式测试注入点，生产缺省null；测试在finally恢复。专用构造注入的writer仍由调用者明确选择，不暗中包装任意writer。
