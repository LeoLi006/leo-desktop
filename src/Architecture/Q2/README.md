# Q2：自定义本机应用启动的最小闭环

本批在 Q1 盘点与草案基础上落地第一个试点；不改变清单、足球、音乐、代理等业务实现，不新增用户功能，不制作发布包或 GitHub 发布材料。

## 已落地

- `CapabilityRegistry` 统一查找旧内置动作、自定义本机应用及旧扩展。内置描述按需构建并缓存；本机应用配置不变时复用描述，配置变化时整体替换对应快照。没有为每个应用增加常驻计时器。
- `local:<ID>`、`local_app_open`、已配置应用对应的 `app_open` 和唯一匹配的 `app_open_name`，在请求合并之前统一为同一个本机应用动作。快捷按钮、搜索、聊天、语音及旧组合/扩展继续使用现有入口。
- `ApplicationCapabilityHost` 只从已保存的配置构造 `ProcessStartInfo`，沿用路径修复、启动参数、工作目录、管理员选项和历史记录。图标、排序、入口位置和名称继续由现有配置管理，不另存一份。
- 同一应用仍在启动时重复触发，合并一次执行；每个调用者保留独立请求 ID、来源和结果。一个调用者取消不影响仍在等待的其他调用者，最后一个调用者离开才取消共享工作。
- 停用、移除、配置变化和退出会取消等待并阻止后续启动；迟到返回不能写成成功或新增历史。经确认的路径修复会更新本次运行使用的配置，避免被下一次设置刷新误判为旧任务。
- 启动操作默认等待15秒、不自动重试。系统启动调用无法被安全中断时，停止等待并保留该应用的在途占用，直到调用返回，避免下一次点击叠加启动。
- 增加结构化结果、最近60条内存结果、请求/执行/合并/成功/失败/取消/超时计数；原 `Task<string>` 调用继续通过兼容适配返回文字或抛出对应异常。没有新增持续日志采集或上传。

## 一条执行链

```mermaid
flowchart LR
  A[按钮 / 搜索 / 聊天 / 语音 / 组合] --> B[兼容入口解析与应用 ID 归一]
  B --> C[CapabilityRegistry]
  C --> D[ActionDispatcher：请求、合并、取消、结果]
  D --> E[ApplicationCapabilityHost]
  E --> F[原配置和路径修复 → 系统启动]
  D --> G[旧模块适配器：其他业务保持原实现]
```

这里复用原 ActionDispatcher，不同时保留两套应用执行器。搜索框普通程序仍采用原路径；命中已配置应用时，统一路径负责启动，不再在 Launcher 中直接 `Process.Start(LocalApplications.Start(...))`。

## 最小契约的边界

见 [MINIMUM.md](MINIMUM.md)。这是宿主内部的 `leo-action/1` 最小子集；**不是新的可安装模块包格式**。外部模块继续 LeoModule/1，一行 JSON 和旧字符串结果不变。

当前结果只落地 succeeded/failed/cancelled。通用排队、部分完成、需要选择、工作流数据引用、全部模块生命周期和独立交付仍未完成，不把这一个应用试点等同于全产品模块化。

## 验证与比较

见 [VALIDATION.md](VALIDATION.md)、[性能对照](COMPARISON.md)。验证使用假启动器，未启动用户应用、切换代理、播放音乐、启用麦克风或调用模型。

新增第二个应用只需要增加 LocalApplication 配置，无需修改 PetForm、聊天工具列表、搜索分支或菜单构造。后续有数据模块的试点继续单独审批。
