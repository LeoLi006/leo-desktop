# Application-location and drop-open maintenance notes

User operations: [Chinese](QUICK_START.md#应用目录与拖放打开) / [English](QUICK_START.en.md#application-folders-and-drag-to-open).

## Existing boundaries reused

- Application tiles remain in `LauncherForm.PopulateRecent`. Their existing favorites/alias menus gain an optional location action. `ApplicationLocation` checks ordinary program targets and current custom application paths; shortcut resolution reuses `Catalog.ResolveExecutable`. Cached shortcut executable metadata may decide menu visibility, but execution resolves the target again. `path_reveal` remains the shared action; `FileDropActions.FolderStart` remains the Explorer selection builder. No protected Store directory lookup or permission changes.
- `DropContent` and the existing `DropActionForm` remain the drop entry/panel. The latter has been moved out of `DropActions53.cs` for readability, not duplicated. The pet's layered form now also receives OLE drop events alongside the existing full-bounds `HitSurface`; pointer drag and dock geometry are unchanged. Tests check native window hits and routed drops at head/face/body points.
- `DropOpenExecution` adapts payloads to the existing `files_with_app` action, dispatched by `ActionDispatcher`. It is not another registry/executor. Existing payloads without `mode` retain `app` semantics. Current modes: `app`, `default`, `code`, `system`, `reveal`. All require explicit absolute `paths`; validate every item rather than silently filtering missing inputs. There is no model API or background poller. No new brain tools or permission scopes are introduced.
- `code` shares `LauncherFileSearch.FindCode/CodeStart`, always including `--new-window`; all paths are appended as separate arguments in one new-window request. File search retains its existing browse fallback. `media_file` still goes through the existing media capability, with passive executable/module checks before offering the single-item button.
- `system` calls Windows `SHOpenWithDialog` with `OAIF_EXEC` for one file. System recommendations stay inside Windows; the code does not infer compatibility from installed apps or maintain a format-to-program list. The picker separately labels configured apps as manual selection and retains its EXE browser. It does not force a default-association change. Shell dialog return is not treated as proof that a file opened.

## Arguments, scope and cancellation

Configured opening reuses `LocalApplications.Start` validation, working directory and UAC verb. Saved arguments are parsed with `CommandLineToArgvW` and transferred individually to `ProcessStartInfo.ArgumentList`; dropped paths are separate arguments. No command interpreter or string-concatenated execution is introduced. Dropped absolute paths are validated without environment expansion, preserving literal percent-delimited names; manually typed paths retain LocalPath expansion before entering the shared Code builder. Third-party applications can still interpret their own arguments differently; manual choice does not imply file-format support.

Default opening and Reveal submit one request per path; Code submits one request containing all paths. Windows Open With, manual apps and PotPlayer deliberately support one item until a meaningful batch contract exists. The panel lists all accepted paths/counts; duplicate paths are merged, over 100 entries are rejected, and the shared action payload-size limit is unchanged. Runnable files omit default execution but retain explicit app viewing and module-add actions. Notes/tasks aggregate the payload; the existing task confirmation has its original title-length limit.

The panel serializes clicks while busy. Close/Dispose cancels its dispatcher token, disposes owned content once, and ignores late results. Cancellation cannot undo requests already passed to Windows. A partial batch error raises an IOException with the submitted count, so the existing dispatcher records failure instead of full success; no automatic replay occurs. Receipts always distinguish a submitted request from observed successful opening.

## Verification scope

Run `--drop-open-test <absolute-report-path>` after building. It uses isolated files and launch doubles: real shortcut target parsing, Explorer selection arguments, Unicode/space/quote/backslash preservation, administrator/working-directory preservation, default/Code/reveal batch scope, unsupported batches, missing paths, cancellation/partial errors, real tile menus, panel close/late completion, keyboard navigation, monitor containment and native full-pet hit points. UI screenshots cover Chinese and English. Fake executables are never launched; no actual user's document, media player or editor is opened.

The existing `--launcher-files-test` covers the shared Code builder and search behavior. Only directly affected old assertions in ProfileBatchTests/Platform53Tests were adapted (structured arguments and deterministic PotPlayer availability); unrelated profile/skin/business suites are not required by this batch. No claim is made that simulated launch acceptance verifies an external application completed opening. Native Open With recommendations, file associations, UAC cancellation details and app-specific format support remain Windows/application responsibilities.

API references: [SHOpenWithDialog](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shopenwithdialog), [CommandLineToArgvW](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-commandlinetoargvw).

## Declarative application capabilities

`Preferences.ApplicationOpenRules` stores rule IDs, names, extension lists, folder/batch declarations, adapter type, enabled state and an optional linked LocalApplication ID. Executable paths, icons, saved arguments, working directories and administrator flags remain in the existing application module. `ResolvedOpenApplication` combines the rule with that module and a passive current state; automatic discoveries are ephemeral LocalApplication records, not a second module registry. Defaults for Code, PotPlayer, annotation, Foxit, Word and Excel are data returned by `Defaults()`. Additional applications require a new configured rule/module, not another drop-panel branch.

Resolution order is an explicit binding (including disabled/missing bindings, never silently bypassed), existing configured apps with a recognized executable identity, the existing catalog, read-only App Paths in user/machine 32/64-bit views and executable-only file-association queries, then the existing Code/media path detectors. Annotation has no detection names and remains unconfigured. Association results are checked against declared executable identities, so a PDF handler is not automatically called Foxit. No full scan, install, registry repair, or default-association write occurs.

`Candidates()` requires all paths to match a rule. It deduplicates actual executable identities across modules/rules/defaults, preserves a default batch action if the specialized app has no batch declaration, and labels the specialized entry as default/type-matched when it replaces the duplicate default entry. Windows recommendations remain in the native chooser. Unavailable and single-item-only matches are disabled, never advertised as supported. Existing entries refresh on activation and execution re-resolves current configuration.

The panel sends `files_with_app` with `mode=capability`, `opener=<rule-id>`, `expected=<rule+module hash>` and exact paths. The existing dispatcher validates/cancels/deduplicates requests. The adapter re-resolves the rule and rejects stale hashes (including new UAC settings), mismatched types, missing paths and unsupported batches. Generic apps share one structured argument builder. Code validates Code.exe and reuses CodeStart, always adding --new-window; conflicting reuse-window arguments are rejected. Media dispatches media_file through the existing media module/queue; its host launch callback also uses the same resolved module flags and validation. No new brain tool, API call, macro operation or arbitrary execution adapter is added.

`ApplicationOpenSettings` works on a cloned draft, references the existing ApplicationEditor, and commits through the existing settings transaction. The module manager also stages/copies the new rules; cancel leaves the original configuration unchanged. Binding a player path synchronizes the existing media path setting, without enabling the media module. Store/config-import validation accepts legacy missing rule fields but validates new declarations. Names/icons are module/rule data; capability state is computed rather than persisted.

`--open-capability-test <report>` covers role/type routing, detection doubles, annotation non-detection, deduplication, per-app batch/UAC/argument behavior, configuration changes, uninstall/disable, original media dispatch, UI icons/language and cancelled drafts. `--drop-open-test` remains the directly related panel/menu/cancellation regression. `--open-capability-report <report>` passively reads only local settings and emits role name/state/configured metadata, without paths, arguments, keys or document content; it never launches a detected program. Native app-specific file handling and security prompts remain outside these fixtures.


## Explicit file-processing handoff

The existing `ApplicationOpenRule` now supports adapter `handoff` with local `ImportScript`. Extensions, module reference, name/icon, program, arguments, working directory and explicit UAC continue to use the same rule/module settings. Mojian and Sumatra roles contain no personal paths. Existing roles remain available; primary ranking limits emphasis to Mojian, Code, Sumatra/default (at most three). Other openers stay secondary. Handoff instances are not deduplicated against a default viewer just because they share an interpreter.

`files_with_app` / `mode=capability` validates the current rule/module stamp, then `FileImportHandoff` validates one input and starts the configured program with structured ArgumentList. The configured script precedes saved flags unless already present in those flags. It appends `--import-request` plus a per-request JSON path; document text never enters arguments. No new model tool, dispatcher, install or resident timer is added.

Protocol `LeoFileImport/1`: UTF-8 request (at most 16KB on the receiving side) has protocol, requestId (32 lowercase hex), input (absolute path). The sibling receipt replaces `.json` with `.receipt.json`, echoes all identity fields and state `imported` or `failed`. Only a matching receipt confirms GUI import, never preview success or conversion. Each request waits at most 20 seconds, with cancellation and bounded 100ms checks while active; temporary known transport files are removed afterwards. No automatic retry/kill/rollback of an external import. A cancelled/timed-out request may already have reached the app, and feedback says so. Scripts lacking this explicit protocol are unavailable for reliable import until adapted. No generic GUI automation is attempted.

Configuration remains private: application sharing packages exclude paths and arguments; usage profiles reference module identities only. Config migration is a local backup/restore feature, not a public share package. No machine-specific interpreter, script or Sumatra path is in source or operation guides. Future handlers require the same receipt protocol and type declaration, not drop-panel branches. Current handoff is single-file only; no unattended generation or batch conversion.

Targeted checks: `--open-capability-test` includes handoff import/failure/timeout/cancellation, identity, stale script, disabled module, deleted input, batch refusal, cleanup, argument reuse, localization and primary ranking. `--drop-open-test` covers existing native hit regions, file arguments and keyboard/drop lifecycle. Mojian separately verifies parameter parsing, receipt/no overwrite, and opt-in isolated real GUI import. These are not proofs that arbitrary third-party handlers are compatible or that a converted document meets typography requirements.

Optional-dependency follow-up: 55 open-capability checks and 15 ClashDock shortcut checks passed with isolated files and mock launchers, including missing programs/scripts/modules, unreadable/corrupt path configuration, launch failures, cancellation and continued panel operation. No real clients were uninstalled or launched during these fault checks. ClashDock now opens its path picker only through an explicit context-menu configuration action; unavailable dependencies do not escape into the host UI. These checks cover the tested faults, not every possible OS/process failure.
