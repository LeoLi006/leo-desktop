# Application-location and drop-open maintenance notes

User operations: [Chinese](QUICK_START.md#应用目录与拖放打开) / [English](QUICK_START.en.md#application-folders-and-drag-to-open).

## Existing boundaries reused

- Application tiles remain in `LauncherForm.PopulateRecent`. Their existing favorites/alias menus gain an optional location action. `ApplicationLocation` checks ordinary program targets and current custom application paths; shortcut resolution reuses `Catalog.ResolveExecutable`. Cached shortcut executable metadata may decide menu visibility, but execution resolves the target again. `path_reveal` remains the shared action; `FileDropActions.FolderStart` remains the Explorer selection builder. No protected Store directory lookup or permission changes.
- `DropContent` and the existing `DropActionForm` remain the drop entry/panel. The latter has been moved out of `DropActions53.cs` for readability, not duplicated. The pet's layered form now also receives OLE drop events alongside the existing full-bounds `HitSurface`; pointer drag and dock geometry are unchanged. Tests check native window hits and routed drops at head/face/body points.
- `DropOpenExecution` adapts payloads to the existing `files_with_app` action, dispatched by `ActionDispatcher`. It is not another registry/executor. Existing payloads without `mode` retain `app` semantics. Current modes: `app`, `default`, `code`, `system`, `reveal`. All require explicit absolute `paths`; validate every item rather than silently filtering missing inputs. There is no model API or background poller. No new brain tools or permission scopes are introduced.
- `code` shares `LauncherFileSearch.FindCode/CodeStart`, always including `--new-window`; all paths are appended as separate arguments in one new-window request. File search retains its existing browse fallback. `media_file` still goes through the existing media capability, with passive executable/module checks before offering the single-item button.
- `system` calls Windows `SHOpenWithDialog` with `OAIF_EXEC` for one file. System recommendations stay inside Windows; the code does not infer compatibility from installed apps or maintain a format-to-program list. The picker separately labels configured apps as manual selection and retains its EXE browser. It does not force a default-association change. Shell dialog return is not treated as proof that a file opened.

## Arguments, scope and cancellation

Configured opening reuses `LocalApplications.Start` validation, working directory and UAC verb. Saved arguments are parsed with `CommandLineToArgvW` and transferred individually to `ProcessStartInfo.ArgumentList`; dropped paths are separate arguments. No command interpreter or string-concatenated execution is introduced. Dropped absolute paths are validated without environment expansion, preserving literal percent-delimited names; manually typed paths retain LocalPath expansion before entering the shared Code builder. Third-party applications can still interpret their own arguments differently; manual choice does not imply file-format support.

Default opening and Reveal submit one request per path; Code submits one request containing all paths. Windows Open With, manual apps and PotPlayer deliberately support one item until a meaningful batch contract exists. The panel lists all accepted paths/counts; duplicate paths are merged, over 100 entries are rejected, and the shared action payload-size limit is unchanged. Runnable files omit default execution but retain explicit app viewing and module-add actions. Notes/tasks aggregate the payload; the existing task confirmation has its original title-length limit.

The panel serializes clicks while busy. Close/Dispose cancels its dispatcher token, disposes owned content once, and ignores late results. Cancellation cannot undo requests already passed to Windows. A partial batch error raises an IOException with the submitted count, so the existing dispatcher records failure instead of full success; no automatic replay occurs. Receipts always distinguish a submitted request from observed successful opening.

## Verification scope

Run `--drop-open-test <absolute-report-path>` after building. It uses isolated files and launch doubles: real shortcut target parsing, Explorer selection arguments, Unicode/space/quote/backslash preservation, administrator/working-directory preservation, default/Code/reveal batch scope, unsupported batches, missing paths, cancellation/partial errors, real tile menus, panel close/late completion, keyboard navigation, monitor containment and native full-pet hit points. UI screenshots cover Chinese and English. Fake executables are never launched; no actual user's document, media player or editor is opened.

The existing `--launcher-files-test` covers the shared Code builder and search behavior. Only directly affected old assertions in ProfileBatchTests/Platform53Tests were adapted (structured arguments and deterministic PotPlayer availability); unrelated profile/skin/business suites are not required by this batch. No claim is made that simulated launch acceptance verifies an external application completed opening. Native Open With recommendations, file associations, UAC cancellation details and app-specific format support remain Windows/application responsibilities.

API references: [SHOpenWithDialog](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shopenwithdialog), [CommandLineToArgvW](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-commandlinetoargvw).
